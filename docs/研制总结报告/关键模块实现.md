本章面向后续开发与维护人员，按照代码的真实执行链路说明规则库、控件 Agent、布局 Agent、微调 Agent 和绑点 Agent 的实现。系统采用“模型理解语义、程序执行确定性计算、Schema 控制结构、前端完成人工确认”的组合方式。大模型不直接修改最终组态文件，而是生成关键词、布局意图、连接关系或微调动作；所有会改变 DaoSCADA JSON 的操作均由前后端受控程序完成，并在关键节点执行结构校验、语义校验或人工确认。

后端由 `app/main.py` 创建 FastAPI 应用，`app/deps.py` 在应用生命周期内初始化 SQLite、控件目录、生成任务管理器和各类 Agent，并通过 `Depends` 注入路由。请求及响应边界统一由 `app/schemas.py` 中的 Pydantic 模型约束，重要输入采用 `extra="forbid"`，防止未声明字段进入业务层。路由层只负责协议解析、依赖获取和异常到 HTTP 状态的映射，实际编排位于 Agent 与 Service 中，几何计算、文本解析、Schema 校验等可复用逻辑位于工具模块。大模型调用通过 `model/llm_client.py` 封装为 OpenAI 兼容异步客户端，对连接失败、超时和限流执行有限次数的指数退避重试。

## 3.1 规则库模块研制

### （1）对应需求

项目要求严格按照 JSON Schema Draft-07 建立 canvas、control、binding 三类组态结构规则，并通过独立枚举字典限定取值，禁止 AI 生成枚举范围外的数据。Python 校验 CLI 应能检查任意 JSON，准确识别字段缺失、类型错误和枚举越界，给出具体错误位置、类型及修改建议，对合法和非法样例的判断准确率达到 100%。研制成果还应包含完整规则文件、枚举数据、校验工具、规则说明，以及至少 3 个合法和 3 个非法示例。

### （2）研制方案

针对结构约束、跨节点业务约束和自然语言语义检查的差异，模块采用“JSON Schema 硬校验 + Python 语义规则 + AI 辅助审查”的分层技术路线。后端通过统一 FastAPI 校验接口提供能力，前端负责 JSON 语法预检、规则浏览和错误展示；Schema、配置文件和注册表作为权威规则数据，模型仅补充难以形式化的语义提示，不参与决定字段类型和枚举是否合法。

### （3）关键实现

**规则库组成。**

规则库不是单一的 JSON Schema 文件，而是由结构规则、业务语义规则、资源注册数据和前端说明数据共同组成。各部分职责如下。

| 规则类型 | 主要文件 | 作用 |
| --- | --- | --- |
| 控件结构规则 | `data/schema/control_schema.json` | 约束控件名称、图片、宽度和高度等素材字段 |
| 画布结构规则 | `data/schema/canvas_schema.json` | 约束 DaoSCADA 画布顶层字段、节点数组及基础属性 |
| 绑点结构规则 | `data/schema/binding_schema.json` | 约束状态面板 `panel.list` 中的标签与 designer 绑点信息 |
| 布局语义规则 | `model/layout_tools/layout_intent_rules.py`、`model/layout_tools/get_intent.py` | 校验设备数量、分组、附件、区域、拓扑和引用关系 |
| 尺寸与角色规则 | `data/layout_config.json` | 定义 root、pipe、valve、meter、sensor 等角色的尺寸范围 |
| 控件目录与映射 | `data/control.jsonl`、控件映射 JSON | 定义标准控件及自然语言词到允许候选的映射 |
| 绑点注册表 | `data/binding.jsonl` | 定义可绑定的项目、设备、属性、数据类型和读写能力 |
| 前端规则说明 | `web/scada/src/data/*Schema.ts`、`rules.ts` | 展示字段说明、派生规则以及合法和非法示例 |

三个后端 Schema 均使用 JSON Schema Draft-07。控件 Schema 要求 `displayName`、`image`、`width` 和 `height` 等字段存在，并通过 `additionalProperties: false` 阻止无关字段。画布 Schema 约束 `v`、`p`、`a`、`d` 和 `contentRect` 等 DaoSCADA 核心字段。绑点 Schema 以实际产物为准，目标结构为节点属性中的 `panel.list` 数组，每个列表项包含显示标签以及项目、设备、属性对应的 designer 路径、键值和类型信息。

**后端校验流程。**

统一校验入口为 `POST /api/validate`，实现在 `app/routers/validate.py`。接口接收校验类别和待校验 JSON 后，按以下顺序执行：

1. Pydantic 首先验证接口请求本身，保证类别和 JSON 数据类型正确。
2. 对 control、canvas 和 binding 类别加载对应 Draft-07 Schema。
3. 调用 `Draft7Validator.iter_errors` 收集全部错误，而不是在第一处错误后停止。
4. 将错误转换为统一结果，包含字段路径、错误消息和 validator 类型，便于前端定位。
5. 对 layout 类别使用 `LayoutFile.model_validate` 和 `validate_layout_file`，因为布局中间表示包含数量守恒、引用有效性和拓扑关系等无法仅靠 JSON Schema 表达的约束。
6. 基础规则检查结束后调用 `ValidateAgent` 执行辅助语义审查，并将模型返回的错误和警告合并到结果中。

Schema 采用按需加载。进程第一次校验某个类别时，通过 `asyncio.Lock` 保证只有一个协程读取文件，文件读取放入 `asyncio.to_thread`，避免同步磁盘操作阻塞事件循环；解析完成后写入 `_SCHEMA_CACHE`，后续请求直接复用。最终 `valid` 的判定依据是错误列表是否为空，警告不会单独使结果无效。

`ValidateAgent` 只承担补充审查职责。模型不可用、超时或输出无法解析时，Agent 返回降级说明，不会推翻已经完成的确定性结构校验。因此，Schema 和程序语义规则是质量门禁，AI 校验是发现字段语义不协调、描述不合理等问题的辅助机制。

**前端规则展示与联调。**

`web/scada/src/stores/ruleStore.ts` 管理规则页面状态。用户输入文本后，前端先调用 `JSON.parse` 拦截语法错误；语法正确时再请求 `/api/validate`，展示后端返回的路径、错误和警告。规则说明、派生约束及示例由 TypeScript 数据文件组织，并经 `rules.ts` 汇总，因而规则页面不需要在运行时解析复杂的 Schema 即可完成分类展示。

当前前端规则说明是后端规则的人工镜像，而不是由 Schema 自动生成。修改字段或枚举时，需要同时检查后端 Schema、Pydantic 模型、前端规则数据、合法与非法示例以及测试用例。尤其是绑点规则，应以 `data/schema/binding_schema.json` 中的 `panel.list` 结构为权威来源；`ValidateAgent` 中的绑点提示也必须随 Schema 同步，避免模型仍按旧的通用变量绑定结构进行审查。

**规则扩展原则。**

新增规则时应根据约束性质选择落点：字段存在性、类型、枚举和附加字段限制写入 JSON Schema；数量守恒、跨节点引用、循环依赖和拓扑一致性写入 Python 语义校验；可配置的角色尺寸及映射关系写入数据文件；提示性和难以完全形式化的检查才交给模型。这样可以保证相同输入在核心规则上得到可重复结果，同时保留模型处理自然语言语义的能力。

## 3.2 控件 Agent 模块研制

### （1）对应需求

项目要求支持“水泵运行状态指示灯”等自然语言 Query，完成 Query 改写以及设备类型、状态、风格等关键实体提取，提取准确率不低于 90%。系统应优先基于 embedding 检索本地素材，相似度大于 0.85 时复用，未命中时调用文生图接口生成不低于 128×128 像素的工业风格素材，并经尺寸、格式和风格质检后入库。模块还应支持素材浏览、搜索、删除和批量生成，管理操作响应时间不超过 100 ms，批量效率不低于 10 个/分钟、素材合格率不低于 95%，并满足 5 条不同 Query 检索准确率不低于 90%的验收要求。

### （2）研制方案

模块采用“受约束关键词提取 + 本地目录优先检索 + 缺失素材异步生成 + 人工确认入库”的技术路线。为降低工业控件误匹配风险，当前实现没有让模型自由改写名称，而是要求提取结果必须为原 Query 中的连续片段；检索按标准名称、受控映射和未知词分级处理，未知词进入文生图任务。素材主数据、业务查询和语义检索分别由 JSONL、SQLite 和 Chroma 承担，确认入库后通过目录热更新形成可持续复用闭环。

### （3）关键实现

**模块职责与数据边界。**

控件 Agent 负责将自然语言中的控件需求转换为可用素材候选。核心代码位于 `model/control_agent.py`，关键词提取位于 `model/control_tools/extract.py`，控件目录管理位于 `model/control_tools/catalog.py`，向量嵌入位于 `data/chroma/embedding.py`。SQLite 数据访问由 `data/sqlite/material_db.py` 完成，缺失素材的生成生命周期由 `app/services/generation_service.py` 管理。

系统区分三类素材数据：

- `data/control.jsonl` 是标准控件目录的权威数据，保存标准名称、图片路径和原始尺寸。
- Chroma 是由标准目录构建的检索投影，只用于语义相似度计算，不能作为素材主数据修改。
- SQLite 的 `controls` 表是便于接口查询的运行投影，`query_results` 表保存用户确认用于本次布局的素材集合。

布局 Agent 只读取 `query_results`，不会直接使用某次搜索返回的全部候选。因此，用户在控件页选择并保存候选，是控件模块和布局模块之间明确的数据边界。

**自然语言提取与结果约束。**

`ControlAgent.process_query` 首先从 `ControlCatalogManager` 获取一个不可变的 `CatalogSnapshot`，并在处理结束后释放。快照保证同一次请求中的标准名称、映射表和 Chroma 集合来自同一版本，即使请求过程中目录发生热更新，也不会出现前后数据不一致。

关键词提取由 `_extract_control_names` 调用大模型完成。提示词要求模型只能返回原查询中连续出现的词，不能改写或补充名称。模型结果进入检索前还要经过程序检查：

1. 输出必须是字符串数组。
2. 使用 NFKC、空白归一化和 `casefold` 生成比较键。
3. 每个词必须确实出现在原始查询中。
4. 重复词被去除，并按其在原句中的位置排序。
5. 第一次输出不合格时允许再次请求，仍不合格则返回明确的模型输出错误。

提取缓存的键同时包含查询文本、模型名称、提示词版本和当前控件名称集合。目录或提示词变化后，旧缓存不会被错误复用。连接错误、服务不可用、超时和模型输出非法分别映射为不同业务异常，路由再转换为可识别的 502、503 或 504 响应。

**分级检索策略。**

提取出的每个词按标准名称、映射词和未识别词三类处理。

| 命中类型 | 处理方式 | 结果特征 |
| --- | --- | --- |
| 标准名称精确命中 | 将标准控件置于首位，同时从 Chroma 取少量相似控件作为备选 | 首选结果确定，备选提供人工选择空间 |
| 控件映射命中 | 只在映射表声明的白名单目标中检索和排序 | 不会越过目录映射返回无关控件 |
| 未命中 | 不执行面向全目录的无约束语义兜底 | 返回 `canGenerate=true` 和缺失名称，引导素材生成 |

这种策略有意限制模型和向量检索的自由度。未知词不会因为向量距离接近就被强行解释成现有控件，从而避免将工业设备需求错误映射到语义相近但功能不同的素材。每个候选携带标准名称、图片、尺寸、相似度及来源，前端据此展示精确结果、映射结果和可生成项。

**控件目录、向量索引与热更新。**

`ControlCatalogManager` 加载 JSONL 时建立标准名称字典和归一化名称字典。重复 `displayName` 采用后出现记录覆盖前记录并记录警告。映射文件加载时校验版本、映射词唯一性、候选数量、目标是否真实存在，以及映射词是否与标准名冲突。

Chroma 使用本地 SentenceTransformer 生成向量，集合名称包含控件 JSONL 内容的 SHA-256 摘要。内容变化时创建新集合，而不是在旧集合上原地修改。`acquire` 会比较目录与映射文件摘要，在锁内完成新快照构建；若重建失败，当前可用快照继续服务。旧快照通过引用计数管理，只有所有正在使用它的请求释放后，其 Chroma 集合才会进入清理流程。若仅映射文件变化，则可复用原向量集合，避免无意义的重新嵌入。

SQLite 初始化时开启 WAL 和外键约束，并将 JSONL 同步到 `controls` 表：新增和变更记录批量写入，目录中已删除的控件从投影表删除。该设计使 JSONL 便于版本管理和人工审阅，SQLite 适合业务查询，Chroma 专注向量召回，三者职责不会混淆。

**缺失素材生成与确认入库。**

前端发现 `canGenerate` 项后，通过 `POST /api/control/generations` 创建图像生成任务。`GenerationManager` 维护 `queued`、`running`、`ready`、`failed`、`confirmed`、`discarded` 和 `expired` 等状态，并使用单个异步队列工作协程串行调用生成服务。文生图 SDK 的同步调用放入 `asyncio.to_thread`，不会阻塞 FastAPI 事件循环。前端 `useGenerationPolling` 每秒轮询任务状态，ready 后显示临时 PNG；用户可以重新生成、放弃或确认。

预览文件具有有效期，后台清理任务定期将过期任务标记为 expired 并删除文件。重新生成会使用新随机种子并清除旧预览，放弃也会清理临时资源。确认操作在 `_confirm_lock` 内执行，主要步骤如下：

1. 再次检查任务状态、过期时间和名称冲突。
2. 将 PNG 转为数据 URL，上传至 DaoSCADA 的 `assets/Agent/{name}.png`。
3. 将 128×128 的生成控件元数据追加到 `control.jsonl`。
4. 重新获取目录快照，验证新控件已完成热加载和索引构建。
5. 同步写入 SQLite 的控件表和查询结果表，使其立即可用于布局。
6. 将任务标记为 confirmed 并删除本地预览。

确认是生成素材进入正式目录的唯一入口。需要注意，远端图片上传、JSONL 追加和 SQLite 提交不是一个跨存储事务；若中间步骤失败，可能遗留未被目录引用的远端资源，或出现 JSONL 已追加但 SQLite 尚未提交的情况。运维清理和后续事务补偿设计应关注这一一致性边界。

## 3.3 自动布局模块研制

### （1）对应需求

项目要求读取画布宽高、素材尺寸和用户 Query，准确提取布局意图，并先用 Mermaid 或流程图 DSL 描述控制流骨架，再规划区域并生成符合 Schema、坐标精度不大于 1 px 的组态 JSON。布局需保证同类设备距离小于 200 px、管路与设备有效连接、仪表和显示控件进入指定区域，并在元素超过 20 个时采用力导向等算法辅助排版。前端预览应支持缩放和拖拽，渲染延迟不超过 1000 ms，对重叠率大于 10%及无连接的非显示控件准确报警，确保 3 个典型场景通过 Schema 校验和人工评审。

### （2）研制方案

模块采用“结构化需求解析 + 布局意图中间表示 + 确定性几何排版 + 独立管道拓扑 + 实时预览”的技术路线。当前代码以类型化 `LayoutFile` 中间表示承载控制流骨架和区域关系，相比自由 Mermaid 文本更便于执行数量守恒、引用和循环依赖校验；常见布局优先使用规则直接生成，复杂拓扑才调用模型。模型负责理解分组和连接意图，控件尺寸、区域、坐标、端口、节点编号及最终 DaoSCADA 结构由程序计算。

### （3）关键实现

**总体生成管线。**

布局入口位于画布路由，核心编排由 `model/layout_agent.py` 的 `LayoutAgent.generate` 完成。输入包括画布标题、宽高和结构化自然语言，素材来自控件阶段已确认的 `query_results`。若没有任何已确认素材，系统直接返回素材缺失错误，避免模型在不知道实际资源尺寸和图片路径的情况下生成布局。

前端布局页将用户输入组织为“控件、流程、结构、管道”四个区段。后端按以下管线执行：

1. 从 SQLite 读取本次可用素材，并建立标准名称词表。
2. 使用 `asyncio.create_task` 并行生成背景画布和布局意图，减少两项外部或复杂任务的串行等待。
3. 校验布局意图中的设备数量、分组、附件、区域和引用关系。
4. 根据画布内容区、角色尺寸及排列方式确定性计算设备坐标。
5. 根据“管道”区段生成连接关系并校验拓扑。
6. 将背景、控件、标签和布局元数据组装为 DaoSCADA JSON，同时将管道关系作为独立数据返回前端。

**背景画布生成。**

`model/layout_tools/get_background.py` 从已有 DaoSCADA 背景模板中选择与目标尺寸最合适的模板。1920×1080、2560×1440 和 1280×960 等常用尺寸优先精确匹配；其他尺寸按宽高比和面积选择最近模板，然后按节点角色缩放。

背景填充、边缘标题条、文本覆盖和自由节点采用不同缩放策略，避免将所有背景元素简单按同一比例拉伸。标题节点会替换为用户输入标题，最终背景仍保持 DaoSCADA 的节点结构，为后续控件编号和内容边界计算提供基准。

**布局意图解析与重试。**

`model/layout_tools/get_intent.py` 先由 `parse_structured_prompt` 解析固定区段。控件清单必须满足“数量 + 单位 + 设备”的形式，解析器支持常见中文数字，并检查重复设备、缺少设备以及控件清单和结构描述之间的数量冲突。流程区段被解析为有序工艺路径和并行标记；管道区段只用于后续连接生成，不参与设备数量推导。

布局意图中的设备词表完全来自 `query_results`。自然语言出现未保存的设备类型时，程序在调用布局模型前就会抛出 `StructuredPromptError`，不会让模型自行虚构素材。对于常见区域、排列和简单流程，`build_rule_layout` 优先直接构建布局中间表示；只有规则无法覆盖或存在复杂拓扑时才调用大模型。

模型返回内容通过 Pydantic 转换为 `LayoutFile`。每个分组描述区域、根控件、附件、实例数量、横向、纵向或网格排列、网格行列、拓扑和相对位置关系。`validate_layout_file` 进一步检查分组 ID 唯一性、实例数量、网格容量、附件引用、库存总量、相对关系和循环依赖。模型输出不合格时最多重试五次，并将上一次的错误类别和摘要加入下一次提示，使模型针对具体错误修正，而不是盲目重复生成。

**坐标与尺寸的确定性计算。**

布局中间表示通过 `convert_layout_file` 转换为实际节点。程序先建立素材映射，按标准名称或受控的包含关系找到素材；任何无法解析到图片和原始尺寸的设备都会中止生成。

坐标计算主要由 `model/layout_tools/compute_position.py` 完成，可分为组级和单元级两层：

- 组级计算以画布 `contentRect` 为可用区域。存在相对关系时按关系形成列，否则按 left、center、right 等区域分配。一个区域内的多个组再按纵向堆叠。
- 每个组根据 horizontal、vertical 或 grid 排列以及行列、间距计算实例槽位。
- 单元级计算以根控件为原点，附件按 top、right、bottom、left 放置到根控件或指定相对节点周围。
- 控件角色优先使用显式配置，其次根据根节点和名称关键词推断，最后落入 default。角色尺寸范围来自 `layout_config.json`。
- 素材在角色尺寸范围内保持原始宽高比，完成一个设备单元后，再将整个单元等比缩小到槽位约 86% 的安全范围；算法只缩小、不放大，避免低分辨率素材被过度拉伸。

`build_nodes` 最终生成 DaoSCADA 控件节点。重复设备的显示名称按实例编号区分，位置和尺寸统一保留两位小数。每个节点还写入 `layout.group`、`layout.node`、`layout.instance`、素材名称和原始宽高等元数据。这些字段既用于后续微调稳定定位，也用于上传前恢复素材比例。

**管道拓扑与序列化。**

只有输入包含“管道”区段时才生成连接。`model/layout_tools/get_connection.py` 根据实际布局节点构建设备目录，大模型只能从目录中的设备、实例和端口生成连接模板。程序校验源端和目标端存在、端口合法、连接不是自环、选择器能解析到实例，并对重复边去重。

如果用户明确写出类似 `A1-B1` 的连接链，显式链被视为拓扑事实。系统会将模型结果与显式边集合比较，缺边、多边或方向相反都会导致失败，而不是静默接受近似结果。通过校验后，程序依据两端几何位置的主要横纵方向规范化端口，使连接更符合实际布局方向。

`model/layout_tools/pipe_serializer.py` 负责将连接模板转换为 DaoSCADA `ht.Edge`。它建立 `(group, node, instance) -> 节点 i` 的索引，拒绝重复索引、重复节点 ID 和找不到端点的连接；随后深拷贝管道模板，写入 `p.source.__i`、`p.target.__i` 和 `layout.role=pipe`，并再次去除重复方向边。

初次布局响应中的画布 `d` 数组只包含背景、控件和标签，管道以 `pipe_data` 独立返回，前端据此进行可交互的 SVG 正交路由。上传时，`CanvasUploadService` 才会根据当前节点位置移除旧受管管线、重新序列化 `pipe_data` 并追加到最终 JSON。这一分离使用户移动控件后可以重算显示路径和最终端点，而不必在每次拖拽时直接修改原始 `ht.Edge`。

**结果组装与前端呈现。**

组装阶段深拷贝背景，为后续微调写入 `layout.materials` 素材快照，按背景现有最大 ID 为新增控件分配节点 ID，并计算 `contentRect` 和修改时间。布局意图、坐标中间结果和管道数据分别原子写入 `layout/it_ir.json`、`layout/pt_ir.json` 和 `layout/pipe.json`，最终组态文件按安全化标题和时间戳保存至 `output`，便于问题复现。

前端 `layoutStore` 保存原始 JSON、控件节点、装饰节点、`pipe_data`、文件名和修订号。`AgentCanvas` 使用 DOM 显示控件与标签，使用 SVG 显示管道，并提供适应窗口、原始比例、缩放和平移。`pipeRouter` 在扩大后的控件障碍区域上执行带转弯代价的正交寻路，无法找到避障路径时退化为简单正交连接。

布局阶段会在日志中记录最终画布 Schema 问题，但不会在此处阻断响应；正式上传还会执行比例校正、重叠检查函数和 Schema 校验。开发新布局能力时，应同时验证中间表示、确定性几何、前端管道路由和上传序列化四个环节，不能只检查模型返回文本。

## 3.4 微调模块研制

### （1）对应需求

项目要求前端支持点击或框选单个及多个控件，选择准确率达到 100%，并完整提取选中元素的 ID、类型、坐标等属性，连同画布 JSON 发送给 AI，属性提取完整率达到 100%。系统应支持换位、改色、对齐、缩放、删除等自然语言指令，AI 仅返回符合 RFC 6902 的 JSON Patch，响应时间不超过 1000 ms，典型指令准确率不低于 80%。前端需提供差异预览、接受、撤销和修改历史，保证撤销后完全恢复且后续操作始终基于最新 JSON。

### （2）研制方案

模块采用“前端直接几何交互 + 模型解析受限动作 + 后端确定性执行 + 最小 JSON Patch + 人工接受或撤销”的技术路线。当前前端通过点击和 Ctrl/Meta 多选完成选择，拖拽与等比例缩放即时更新画布；自然语言请求则由模型输出动作对象，后端完成边界、比例、碰撞和标签处理，再编译为补丁。该方案避免模型直接构造全量 JSON，也为版本校验、补丁预览和完整回滚提供稳定基础。

### （3）关键实现

**前后端职责划分。**

微调采用两条互补路径。拖拽和缩放属于前端直接几何操作，结果即时写入当前画布；自然语言微调由后端将语句解析为受限动作，再编译成 JSON Patch，必须由用户接受后才成为确认版本。

前端进入微调页时，只加载与当前布局文件名和修订号匹配的最新画布，并深拷贝 JSON 与管道数据。控件通过点击选择，按 Ctrl 或 Meta 可以多选，点击空白处清空选择。AI 请求执行中或存在待确认补丁时，交互被锁定，防止用户修改画布后又应用基于旧版本生成的补丁。

**直接拖拽与等比例缩放。**

`AgentCanvas.tsx` 和 `dragGeometry.ts` 负责直接操作。拖拽开始时记录全部选中控件的初始位置，将屏幕位移除以当前缩放比例得到画布位移，再根据多选包围盒统一限制在画布内。这样可以保持控件之间的相对位置，不会因为逐个裁剪导致队形变形。坐标写回时保留两位小数，并同步移动与控件关联的标签。

单个控件提供八个缩放手柄。缩放算法使用节点元数据中的素材宽高比，按手柄方向计算新包围盒，并结合画布边界限制尺寸和位置，因此不会产生负尺寸或越界控件。直接操作每次完成后递增修订号，使绑点页能够识别来源已变化。

**自然语言动作解析。**

后端入口调用 `model/refine_agent.py`。`_read_layout` 只将带有 `a.layout.node` 元数据的节点视为可编辑控件，并检查画布宽高、节点 ID 唯一性、几何值有限性，同时建立控件到关联 `ht.Text` 标签的稳定目录。提示词向模型提供画布尺寸、被选中的稳定 ID、当前几何目录和布局阶段保存的素材快照。

当前代码允许的动作如下。

| 动作 | 作用 | 主要约束 |
| --- | --- | --- |
| `move` | 相对或绝对移动 | 绝对坐标只允许单目标，不能混用绝对与相对参数 |
| `resize` | 按比例或目标宽高缩放 | 比例与宽高参数互斥，结果受画布边界和素材比例约束 |
| `delete` | 删除控件 | 同时删除关联标签，后续前端清理相关管道 |
| `align` | 多控件边缘或中心对齐 | 至少两个目标，对齐类型必须在白名单内 |
| `distribute` | 水平或垂直等距分布 | 至少三个目标，按当前位置排序后计算间距 |
| `swap` | 交换两个控件的位置 | 目标必须恰好为两个，各自尺寸保持不变 |
| `add_label` | 为目标增加文字标签 | 校验标签文本、目标和放置空间 |
| `add_control` | 从素材快照新增控件 | 候选名称受素材快照限制，执行碰撞和安全区域检查 |

模型只能返回 `message` 和 `actions`。`_validate_model_data` 对动作字段执行白名单检查，拒绝未知目标、重复目标、互斥参数、非法枚举和超出数量限制的候选。当前实现不包含任意改色、任意属性写入或直接提交 JSON Patch 的模型权限；扩展动作时必须同时增加输入校验、确定性执行逻辑和补丁路径白名单。

**确定性动作执行。**

模型通过校验后，`_apply_actions` 在后端副本上执行实际修改。移动和缩放统一限制在画布边界内；对齐分别按左、右、上、下、水平中心或垂直中心计算；分布先按对应轴排序，再在首尾节点之间等距布置；换位只交换坐标；删除时同步定位和删除关联标签。

新增标签根据文本长度估算宽度，宽度至少覆盖目标控件，高度固定为可读尺寸。算法优先放在控件上方，空间不足时改放下方；多选批量加标签还要求目标控件图片类型一致。新增控件是更复杂的受控动作，并且必须是一次模型响应中的唯一动作，其目标集合必须与用户当前选择完全一致：

1. 从 `layout.materials` 中按标准名称查找素材，模型最多给出有限个候选。
2. 候选不唯一时返回歧义，而不是由程序猜测。
3. 以一个或多个已选控件为锚点，在指定方向及轮换方向上尝试放置。
4. 检查画布安全区、已有控件障碍和控件间间隔。
5. 空间不足时统一缩小新增控件，最低允许约为原目标尺寸的 50%。
6. 写入与布局节点一致的元数据，并重新计算内容边界。

这种方式使大模型只决定“做什么”，坐标、尺寸、碰撞和 DaoSCADA 节点结构仍由程序决定。

**JSON Patch 编译与确认机制。**

动作执行完成后，`_compile_patch` 比较修改前后的节点，只输出发生变化的 add、replace 和 remove 操作。数组删除按索引倒序生成，避免前一项删除后导致后续索引偏移。`_validate_patch` 再次检查操作类型、允许路径、数值有限性和样式对象结构，确保补丁不能越过预定字段修改画布其他内容。

前端 `refineStore.ts` 通过 copy-on-write 方式应用 RFC 6902 子集。在应用前保存 JSON、管道和选择状态快照，形成 `pendingPatch`；应用后重建控件与装饰节点，并移除指向已删除控件的管道。用户接受时清除待确认标记并写入历史，拒绝时从深拷贝快照完整恢复。绑点模块在存在待确认补丁时拒绝取得微调来源，只有已接受且与当前布局文件匹配的微调结果才会覆盖布局结果。

每次请求还记录提交时的 JSON 对象身份和请求所有权标记。若用户已切换布局、重新提交请求或当前画布不再是原版本，迟到的异步响应会被丢弃，从而避免旧补丁覆盖新画布。

## 3.5 数据绑点模块研制

### （1）对应需求

项目要求上传 Excel 设备变量清单，通过模糊列名识别变量名、数据类型和寄存器地址等字段，解析准确率不低于 95%。匹配算法应结合 embedding、同义词和编号关系关联控件与后台变量，输出候选及匹配依据，并以 100%的准确率识别同一地址多控件绑定和变量名重复等冲突。前端需提供可人工修改和确认的表格复核界面，标准清单 Top-1 匹配准确率不低于 75%，能够识别 3 条预置冲突，最终绑点 JSON 必须通过 Schema 校验。

### （2）研制方案

模块采用“清单硬校验 + 本地注册表约束 + 精确匹配优先 + BGE 语义召回 + 人工确认 + 原子构建”的技术路线。当前实现将输入收敛为固定两列表头的 CSV，而不是直接解析 Excel 和模糊列名；绑定对象只能来自本地注册表，前端提交后后端还会重新计算候选并验证 assignment，防止伪造或过期选择。不同控件类型通过 `BindingHandler` 扩展，已确认结果写入画布副本并同时接受画布 Schema 和绑点 Schema 校验。

### （3）关键实现

**输入清单与绑定注册表。**

绑点模块采用“CSV 需求清单 + 本地绑定注册表 + 当前画布”的三方匹配。CSV 由 `app/services/csv_service.py` 解析，当前只接受 `.csv`，不接受 Excel 文件。解析器执行以下硬性检查：文件不超过 5 MB，数据行不超过 10000 行，编码依次支持 UTF-8 BOM、UTF-8 和 GB18030，表头必须严格为 `displayName,propertyName`，每行必须恰好两列，空值和重复的显示名称/属性组合都会报错。空白行忽略，但错误信息保留物理行号，便于定位源文件。

`data/binding.jsonl` 是可绑定属性的权威注册表。`app/services/binding_config_service.py` 在加载时校验必填字段、数字字符串形式的项目/设备/属性 ID、double、int、bool、string 数据类型、布尔型 writable、可选单位，以及绑定 ID 和物理来源组合的唯一性。任何注册表错误都会汇总并阻止 `BindingAgent` 初始化，采用启动期失败而不是运行时跳过坏数据，避免错误绑点在生产流程中悄然出现。

**处理器机制与目标定位。**

不同 DaoSCADA 控件的绑定落点可能不同，因此后端定义了抽象 `BindingHandler`。当前实现注册 `PanelListHandler`，只处理显示名称为“状态面板”或带正整数后缀的实例，例如“状态面板2”。处理器将实例名归一化为“状态面板”，目标类型必须是 `ht.Node`，读写位置为节点属性 `a.panel.list`。

匹配开始时，Agent 按 CSV 的 `displayName` 在画布中查找目标。不存在、同名节点多于一个、节点类型不支持或没有可用处理器都会形成逐行错误。内部目标使用画布 `d` 数组索引而不是节点显示 ID 作为写入位置，确保后续深拷贝画布时能够准确修改原节点。

`PanelListHandler` 输出的每个列表项包含显示标签和 designer 绑定结构。路径按 `project#device#property` 生成，键按 `device#property` 生成，并写入项目、设备、参数及数据类型；存在单位时才在标签中附加单位，不会产生空括号。

**精确匹配与语义召回。**

`app/services/semantic.py` 以进程级单例加载本地 BGE 中文嵌入模型，并设置 `local_files_only=True`，保证运行阶段不会临时从网络下载模型。注册表属性在 Agent 初始化时预编码为归一化向量，查询属性按处理器和标准控件名分组批量编码，避免逐行重复调用模型。

候选生成优先执行属性名精确匹配。只有一个精确项时直接返回，分数为 1；若注册表中存在多个同名精确项，则由于无法区分物理来源，系统不自动给出建议。没有精确项时使用归一化向量点积计算余弦相似度：

`score = normalized_query_vector · normalized_binding_vector`

候选按分数降序、绑定 ID 稳定排序，只保留分数不低于 0.55 的前五项。除最高分外，系统还计算领先差值 `lead = top1 - top2`，用于识别第一候选是否明显优于第二候选。

| 置信度 | 判定条件 |
| --- | --- |
| high | `score >= 0.85` 且 `lead >= 0.08` |
| medium | `score >= 0.70` 且 `lead >= 0.05` |
| low | `score >= 0.55`，但未达到更高等级 |

接口返回候选、分数、领先差值、置信度和匹配依据，最终选择仍由用户完成。只有所有行都没有任何候选时，匹配结果才整体标记为 blocked；部分行失败时，其他可匹配行仍可继续确认。

**绑定构建与原子校验。**

前端构建时只提交用户已确认的 assignment。后端不会信任前端传来的候选，而是使用原始 CSV 和当前画布重新执行一次匹配，并进行以下检查：

1. 同一 CSV 行不能重复提交 assignment。
2. assignment 必须对应真实输入行。
3. 绑定 ID 必须存在于本地注册表。
4. 所选绑定必须确实出现在该行重新计算的允许候选中，防止伪造 ID。
5. 同一目标节点不能重复选择同一个绑定 ID。

通过检查的 assignment 按目标节点分组，并保持 CSV 行顺序。处理器为每个目标重新渲染完整 `panel.list`，再写入原画布的深拷贝。未确认行不写入，计入 skipped 并返回警告。完成写入后，系统同时校验完整画布 Schema 和每个 `panel.list` 的绑点 Schema；任一处失败都令 `bound_json` 为空，不会返回部分有效、部分无效的绑定文件。响应同时包含应用数、跳过数及绑定前后预览，供前端复核。

**前端来源控制与最终上传。**

`bindingStore.ts` 通过文件名和修订号确定绑点来源。若当前存在待确认的微调补丁，则来源为空并阻止继续；若存在与当前布局匹配的已确认微调结果，则优先使用微调画布；否则使用原布局。来源修订号变化时，Store 深拷贝新画布并清除旧候选、确认状态和构建结果，避免将旧 assignment 应用到新节点位置或新设备集合。

用户可以逐条选择候选并确认，也可以批量确认。修改某一行的候选会自动取消该行原确认状态。构建成功后，前端展示绑定前后差异，再调用 `CanvasUploadService` 生成 `{原文件名}_bound.json` 并上传 DaoSCADA。

上传服务是最终一致性门禁。它校验文件名和画布尺寸，根据节点中的 `layout.sourceWidth`、`layout.sourceHeight` 或素材库唯一记录恢复控件原始比例，在现有包围盒内执行等比例内接，并同步关联标签。若提供当前管道数据，则删除旧受管管线并按最新节点位置重新序列化；随后重新计算 `contentRect` 并执行画布 Schema 校验，只有结构校验通过时才向 DaoSCADA 发送组态 JSON。

`CanvasUploadService._collision_warnings` 的设计目标是比较比例校正前后的矩形，阻止新增重叠或重叠面积扩大。但当前 `upload_canvas` 在控件尺寸已经改写后才构造 `before_rects`，使传入的 before 和 after 实际相同；现状只能对校正后仍然重叠的控件产生 warning，无法可靠区分“原有重叠”和“校正新增或扩大重叠”。修复时应在调用 `inscribe_ratio` 前保存原始矩形，再将原始矩形与 `corrected_controls` 传给 `_collision_warnings`，并补充新增重叠、扩大重叠、原有重叠缩小三类测试。

当前绑点实现的明确边界是：输入仅支持 CSV，处理器仅覆盖状态面板的 `panel.list`，程序强制检查同一目标内的重复绑定，但不禁止不同目标复用同一注册项。新增仪表、表格或其他控件绑点时，应新增对应 `BindingHandler`，定义目标识别、候选目录分组、现有绑定读取和目标结构渲染，并补充 Schema 与端到端测试，而不应在 `BindingAgent` 主流程中硬编码控件特例。

五个模块通过明确的数据产物衔接：规则库约束全部输入输出，控件 Agent 产生经用户确认的素材集合，布局 Agent 产生画布和独立管道关系，微调 Agent 产生可接受或撤销的增量修改，绑点 Agent 在最新确认画布上写入属性关系，上传服务完成最终比例、管道、重叠和 Schema 校验。该链路将概率性模型输出限制在可验证的中间结果中，使每个阶段都具备独立测试、错误定位和后续替换能力。
